# Security hardening — 18/09/2026

## Scope

This patch hardens the AI-CLO PTITHCM Supabase backend without changing the current frontend workflow.

The student assessment flow remains:

`start_exam_attempt` → `save_exam_progress` → `submit_exam_attempt`

These RPCs are `SECURITY DEFINER` functions owned by PostgreSQL and contain their own ownership / subject-role checks.

## Critical fixes

### 1. Block profile role escalation

A non-admin user could previously update their own `profiles` row, including fields such as `role` and `is_active`.

The patch adds `guard_profile_sensitive_update()` and a `BEFORE UPDATE` trigger on `public.profiles`.

For a non-admin updating their own row, these fields are now protected:

- `id`
- `role`
- `is_active`
- `locked_at`
- `locked_by`
- `email`
- `mssv`
- `created_at`

Normal self-profile fields such as `full_name` remain compatible with the existing policy.

### 2. Block direct score / attempt manipulation

Students no longer have direct INSERT/UPDATE policies on `exam_attempts`.

Attempts must be created by `start_exam_attempt()`. This prevents bypassing:

- exam status
- open / close time
- max attempts
- attempt numbering

Students also cannot directly modify:

- `score`
- `submitted_at`
- `exam_id`
- `attempt_number`

### 3. Block forged final answers

Students no longer have direct INSERT/UPDATE policies on `student_answers`.

`student_answers` is now server-generated by `finalize_exam_attempt()`, so `is_correct` cannot be forged from the browser.

### 4. Enforce timer through the RPC path

Students no longer have direct INSERT/UPDATE policies on `attempt_draft_answers`.

Draft answers are written through `save_exam_progress()`, which checks:

- attempt ownership
- whether the attempt was already submitted
- time limit
- selected option
- question membership in the attempt

This closes the path where a client could write a draft after the timer expired and then finalize it.

## RPC hardening

Anonymous EXECUTE was removed from the assessment RPCs and other logged-in assessment functions.

Direct EXECUTE was also removed from trigger-only / event-trigger-only helper functions.

After the patch, the Supabase Security Advisor no longer reports anonymous `SECURITY DEFINER` functions callable through the API.

## Function search_path

`public.set_updated_at()` and `public.normalize_question_text(text)` now have a fixed:

`search_path = public, pg_temp`

This resolves the mutable-search-path warning for these functions.

## Production post-check

Immediately after applying the patch:

- 27 submitted attempts were compared against their `student_answers` rows.
- Score mismatches found: **0**.
- Sensitive assessment RPCs: `anon EXECUTE = false`, `authenticated EXECUTE = true`.
- Profile guard trigger is active.

## Remaining advisor items

These are not part of this patch:

1. `pg_trgm` is installed in the `public` schema. Moving an installed extension can affect existing SQL references, so it was not changed automatically.
2. Supabase Auth leaked-password protection is disabled. Enable it from the Auth password-security settings.
3. `attempt_live_state` and `attempt_monitor_events` have RLS enabled with no direct policies intentionally; they are accessed through guarded RPCs.
4. The advisor still lists authenticated `SECURITY DEFINER` functions. Many are intentionally callable by signed-in users and contain role / ownership checks. They should be reviewed individually rather than disabled globally.
